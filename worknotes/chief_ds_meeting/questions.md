# Questions for the CDS
_CDS design meeting, 2026-10-15 · session 2, after the feedback on session 1 · about 15–20 minutes · draft_

**How to read this.**
- **Confirm** items are things we plan to do; we take them as agreed unless someone objects.
- **Discuss** items need an answer, or at least need raising so they stay visible.
- ★ = ask even if time is short · *(new)* = not yet tracked in the roadmap · small grey codes =
  where the answer gets recorded.

**Order:** (a) → (b) → (d) → (e) → (f) → (c).

| Topic | Questions |
|---|---|
| **(a) Scope** | **Discuss**<br>a1. ★ First release: binary only, or binary plus one more task type (our proposal: regression)? Either way, we design regression's shapes now, so shared outputs (scores, registry, monitoring tables) don't assume binary. <sub>OD-15</sub><br>a2. ★ Modelling paths in the first release: FLAML AutoML only, or also a predefined model family tuned with Optuna? Checked on our pinned FLAML: it can be limited to one model family with our own search ranges, so "FLAML only" can still offer a predefined family. <sub>OD-15</sub><br>a3. *(new)* After the first release, what release rhythm is realistic, and is there capacity to keep building? The LDS doubts much gets built between two releases only 2–3 months apart, which argues for a smaller first release. <sub>OD-15</sub><br>a4. Eventually, which task families should the framework cover: binary, regression, multiclass, time-to-event, forecasting, nearby problems (uplift, recommendation, segmentation)? *(new)* And should regulated models (e.g. credit risk) ever run through it? That would raise the bar for validation and documentation. <sub>OD-21</sub> |
| **(b) Consumption** | **Discuss**<br>b1. ★ A versioned Python library used through guided notebooks, a CLI and a Python API, with no service. Is that the right model for the unit, rather than a central service or platform? Our reasons: a service means running a platform, and users learn and debug by seeing under the hood. <sub>D-024</sub><br>b2. Once the code sits in an internal repo, how do use cases get it: from an internal package repository where each use case pins a version, or by git clone? Who publishes releases, and must CI/Sonar pass first? <sub>OD-04</sub><br>b3. Where does a use case live (a repo per use case, per domain, or something else), and how do users get the guided notebooks? <sub>OD-02</sub><br>**Confirm**<br>b4. Each use case pins the framework version it runs with and upgrades at its own pace. Nothing is pushed centrally. <sub>D-047</sub> |
| **(d) Structure** | **Discuss**<br>d1. ★ The stage structure: Target Factory (optional) → EDA → Feature Checks → Training → Evaluation → register → promote → deploy → Inference → Monitoring. Each stage runs alone from the config and writes its own report. Is anything missing, merged or in the wrong place? <sub>D-028</sub><br>d2. ★ Do we keep the current folder structure that mirrors the permission barriers (separate parent folders per entity × domain)? Are storage permissions actually separate per entity? <sub>OD-06</sub><br>d3. The first release reads features from the existing upstream marts. Long term, should the framework stay a consumer of those marts, or also own feature aggregation? <sub>OD-19</sub> |
| **(e) Promotion, deployment, consumption** | **Discuss**<br>e1. ★ The original plan had a part-time ML engineering lane for registration, the deployment path and drift alerting. Is that capacity still there, who would it be, and when could they join? If this becomes the unit's new registry type, we don't want to design it alone. <sub>OD-23</sub><br>e2. ★ The lifecycle steps: **register** (local → registered), **promote** (choose the version for production; the approved PR is the sign-off), **deploy** (the change-request process copies it to production). A data scientist's session never writes to production. Does this match how you see it, and what should "registered" mean: any run someone wants to keep, or a gated candidate for production? <sub>D-033, OD-09</sub><br>e3. Versions: how many per model, exactly one in production at a time, and do we want shadow challengers (a new version scoring next to production before it takes over)? <sub>OD-07</sub><br>e4. Registry storage: our own append-only records with tables on top (shaped like MLflow's, so a later move is a mapping), or MLflow itself? <sub>OD-08</sub><br>e5. Deployment copies the model to production paths, rather than pointing production at sandpit paths. Agreed? <sub>lifecycle.md</sub><br>**Confirm**<br>e6. First release, production step: outside the bank, `deploy` runs against a production-tier path on synthetic data; inside the bank, the first change request runs it. <sub>D-055</sub> |
| **(f) Monitoring** | **Discuss**<br>f1. ★ Tooling: our view is that MLflow suits the registry and experiment tracking, not tracking decay over time. What should monitoring use, what is shown, and where do the dashboards live? <sub>OD-13</sub><br>f2. *(new)* Who acts on a monitoring flag (the model owner, a central team?), and who owns a live model once the person who built it moves on?<br>f3. Model inventory: what should an overview of every live model show, and who uses it? <sub>OD-14</sub><br>**Confirm**<br>f4. First release: health (did scoring run, row counts, score distribution) and drift are deep; realised performance and business impact are thin, but must work as soon as outcomes arrive. <sub>D-040</sub> |
